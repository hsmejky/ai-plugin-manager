# Verifying a setup

How to verify the Project setup and Machine setup of a project that uses a Shared plugin, in Claude Code and Codex. This is the only place that describes the verification steps. Complete the [per-machine steps](claude-codex-sharing.md#per-machine-steps) first.

## Run the setup checker

The `check-setup` skill verifies both Hosts and needs Node.js 20 or later. Run it from the project root:

- Claude Code: `/ai-plugin-manager:check-setup`
- Codex: `$ai-plugin-manager:check-setup`

The live checks are opt-in and run only when you ask for them ("live check", or the argument `live`). L1 makes one model call per Host and plugin and needs network and authentication. L2 (latest release) makes no model call; it reads the npm registry over HTTPS and needs network (no npm process). A skipped live check reflects a network, authentication or sandbox limit, not a broken setup.

## Read the report

The report starts with a summary line (counts of fail, warn, skip and pass), followed by one table per group, in this order: Claude Code / Project setup, Codex / Project setup, Both Hosts / Project setup, then the same three for Machine setup; empty groups are omitted. Each finding has:

- a check id (see [the checklist](../../skills/check-setup/checklist.md) for what each check verifies, why, and how to fix it)
- a status: `pass`, `warn`, `fail` or `skip`
- a fix, shown for `warn` and `fail`

Apply the fixes and rerun until no `fail` remains. A `fail` makes the script exit 1; that is a normal result, not an error.

## Verify by hand

Run each prompt non-interactively in each Host from the repository root.

Skills:

```
claude -p "List the names of all skills available to you that come from the <plugin> plugin. Output only the names, one per line, or NONE. Do not run any tools."
codex exec --skip-git-repo-check "List the names of all skills available to you that come from the <plugin> plugin. Output only the names, one per line, or NONE. Do not run any tools."
```

Pass: each Host lists every skill it should offer the model. Each Host hides a user-only skill by a different setting: Claude Code by `disable-model-invocation: true` in `SKILL.md`, Codex by `policy.allow_implicit_invocation: false` in the skill's `agents/openai.yaml` (Codex ignores `disable-model-invocation`; it hides the skill only for exactly `false`, and `$<plugin>:<skill>` still loads it; bare `$<skill>` does not). So the two lists equal each other only for skills that set both or neither; compare each Host against the skills in the `skills` array of the plugin manifest (`.claude-plugin/plugin.json`) that the Host does not hide, not against the full command list or every `SKILL.md` in the plugin's source repository. `check-setup --live` warns when the two settings disagree for a skill.

Run live with codex-cli 0.162.1 on 2026-10-14: `codex exec` listed every `mattpocock-skills` skill except the hidden ones; the plugin-qualified `$mattpocock-skills:ask-matt` loaded `ask-matt`, while bare `$ask-matt` replied NOT LOADED. So a skill with `allow_implicit_invocation: false` is invoked only as `$<plugin>:<skill>`. The rule also follows from Codex source (`openai/codex` tag `rust-v0.162.1`, [research](../research/codex-skill-visibility-invocation-policy.md)).

Instructions:

```
claude -p "In which language must project artifacts be written, according to the project instructions? Answer in one word. Do not run any tools."
codex exec --skip-git-repo-check "In which language must project artifacts be written, according to the project instructions? Answer in one word. Do not run any tools."
```

Pass: both answer `English` (the project language rule in `AGENTS.md`). Any specific rule from `AGENTS.md` works. Automated, opt-in: see [Live instructions and negative checks](#live-instructions-and-negative-checks).

Negative check: run the `codex exec` skills command from a directory outside the repository. It must output `NONE`, provided the plugin is not also enabled in the user-level Codex config. Automated in the same opt-in test.

## Setup skill

Run the plan step against the real Hosts (read-only: it runs only `--version` and `list --json`): `node skills/setup/scripts/setup.mjs plan`. Do not run `apply` on the real machine to test; the live test does it in temporary homes: `SETUP_LIVE=1 node --test skills/setup/scripts/test/live-setup.test.mjs` ([`live-setup.test.mjs`](../../skills/setup/scripts/test/live-setup.test.mjs); network, no login). It seeds trust in temporary `CLAUDE_CONFIG_DIR`, `HOME`, `USERPROFILE` and `CODEX_HOME` and a temporary git copy of the Project setup, runs `plan`, `apply --expect`, check-setup and a second `plan`, and checks that the committed files keep their bytes, that each Host's install contains `skills/check-setup/scripts/check-setup.mjs` and `skills/setup/scripts/setup.mjs`, that the installed `setup.mjs plan` runs in both installs (a broken `../../check-setup/` import fails the test), and that the real `~/.codex/config.toml` and `~/.claude/settings.json` keep their SHA-256 (`~/.claude.json` only must not mention the test project: a running Claude Code session rewrites it itself).

By default the Hosts install what the Project setup's marketplace resolves to, the default branch of `hsmejky/ai-plugin-manager`, so the test fails on `skills/setup/scripts/setup.mjs` until the setup skill is on that branch. To test an unmerged change, push the branch and set `SETUP_LIVE_REF=<branch or tag>`: the test then pins the ai-plugin-manager marketplace in its temporary copy of the Project setup (`ref` in the Claude Code source and in the Codex `config.toml`), never in the committed files. Example: `SETUP_LIVE=1 SETUP_LIVE_REF=integration/setup-skill-71 node --test skills/setup/scripts/test/live-setup.test.mjs`.

Result (Claude Code 2.1.299, codex-cli 0.162.1, Windows, 2026-10-14): passed. The named `codex plugin marketplace upgrade <name>` installs the enabled plugins of a fresh, trusted project (Codex `plugin list` failed before it and showed both plugins installed after it), so the skill uses the named form.

Re-run from the unmerged branch (`SETUP_LIVE_REF=integration/setup-skill-71`, Claude Code 2.1.299, codex-cli 0.162.1, Windows, 2026-10-14): passed, including `skills/setup/scripts/setup.mjs` in both installs and the installed `setup.mjs plan` (Claude Code install and Codex cache version 0.6.0). The same run without `SETUP_LIVE_REF` failed on the missing `skills/setup/scripts/setup.mjs`, as expected while `main` has no setup skill. Codex also lists the skill from the install: `codex app-server` `skills/list` (no login) in a temporary `CODEX_HOME` with the branch installed returned `ai-plugin-manager:setup` and `ai-plugin-manager:check-setup`, and `codex debug prompt-input` (the model-visible list) contained only `ai-plugin-manager:check-setup`, so `setup` is hidden from the model.

Still manual (not Host behaviour claims; the Host claims are in [Manual checks of Host behaviour](#manual-checks-of-host-behaviour)): Linux and macOS live runs of the setup skill.

### Live instructions and negative checks

The instructions check (both Hosts) and the negative check (`codex exec` outside the repository) run as opt-in live tests: `CHECK_SETUP_LIVE_INSTRUCTIONS=1 node --test skills/check-setup/scripts/test/live-instructions.test.mjs` ([`live-instructions.test.mjs`](../../skills/check-setup/scripts/test/live-instructions.test.mjs)). They make model calls and need network and logged-in Hosts; without the variable they skip. Each Host runs in fresh temporary homes (`CLAUDE_CONFIG_DIR`, `HOME`, `USERPROFILE`; `CODEX_HOME`), never the real config, and the test deletes them after each Host run, pass or fail. Credentials (#53): the test only reads `~/.claude/.credentials.json` and `~/.codex/auth.json`, and no Host receives a refresh token, so no Host can refresh or spend the real login's refresh token. Claude Code gets only the access token in `CLAUDE_CODE_OAUTH_TOKEN`, which it uses for the whole session without refreshing ([authentication docs](https://code.claude.com/docs/en/authentication#authentication-precedence), Claude Code 2.1.299); Codex gets a copy of `auth.json` with `tokens.refresh_token` blanked, because it refreshes with the token in its own `CODEX_HOME` (codex-cli `rust-v0.162.1`, `codex-rs/login/src/auth/manager.rs`). A Host is skipped when its file is missing or its access token expires within 15 minutes: run that Host once normally to refresh the real login, then rerun. The test header cites the source lines. Because the temporary Codex home enables no plugin, the negative check also satisfies its proviso. Passed on Claude Code 2.1.299 and codex-cli 0.162.1 (Windows, 2026-10-14), also with this credential handling: the real credential files kept their SHA-256 and modification time, and no credential copy remained in the temporary directory.
